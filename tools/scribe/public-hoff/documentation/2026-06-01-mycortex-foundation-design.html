myCortex v0 — Foundation Design

Date: 2026-06-01 Status: Approved (design); spec under review Owner: the Hoff

Purpose

myCortex is the Hoff's own agentic OS — a core framework to drive multiple models seamlessly, reusable across the council and other projects. v0 forks the cortextOS runtime as its base, encodes the project's four laws as enforced convention, and stands up the two capabilities that make those laws real: parallel agent workstreams and an advisory tri-model peer-review gate.

This is not greenfield: cortextOS already provides the Foreman-shaped runtime (persistent agents, PTY backends, Telegram bus, dashboard). We build on top and keep our work back-portable.

The five laws (project constitution)

  1. Parallel agent workstreams. Decompose work across isolated agents in git worktrees as the default. This applies to coding workers (each peer can own a workstream) as well as reviews — not just one model at a time.
  2. Mandatory tri-model peer review. Every substantive change is reviewed by Codex + AGY (Gemini/Antigravity) + OpenCode (MiniMax 2.7) before merge. Claude is the driver, so review is the other three voices. Enforced as an advisory git hook (overridable), not a hard block.
  3. Build on top, stay bidirectional. We must always be able to PR back upstream and pull/merge upstream down. Therefore every addition is classified as exactly one of two kinds — nothing in between, because in-between edits break one or both directions of that flow:
    • (a) Disconnected / modular — a pluggable module that does not modify the base. The base exposes (or we upstream) an extension point; our behaviour drops in as a plugin. Exemplar: the Hoff's pluggable Telegram comms — swappable communications modules, base untouched. This is the preferred kind.
    • (b) Supportable, justifiable upstream PR — a change to the base that cortextOS would plausibly accept: generic, tested, broadly useful. If we must touch the base, it has to be PR-worthy on its own merits.
    • Corollary — abstraction over hardcoding. Where we'd otherwise bake in Hoff-specific behaviour, contribute a generic extension point (kind b) and ship the Hoff-specifics as a plugin (kind a). First instance: theming — uplift cortextOS to support themes (PR-worthy), then ship hoff-ui as a theme plugin (modular).
    • A BACKPORT.md ledger tags every addition (a) or (b), so divergence stays legible and the merge path never silently rots.
  4. Local-first ownership. Everything tracked in local git (lab Gitea is primary, origin GitHub secondary). upstream is a lifeline, not a master. "This is mine for now."
  5. Minimal-AI / cheapest-competent-worker. Mechanical jobs are done by the cheapest worker that can do them well, looking like an agent on the bus. Order of preference: (1) deterministic Node.js program; (2) a tiny local edge model (≤~1GB, mlx / GPU / CPU — the Hoff can train these, see mlx-llm) for jobs that are mechanical-but-fuzzy; (3) the frontier model peers, reserved for genuine generation and judgement. This is "minimal-AI" by resource and cost, not zero-AI dogma. HARD RULE: Node.js for everything we build — harness, workers, glue, scripts. Not Python/bash/bun for our own code. (Invoking third-party tools on other runtimes is fine.)

Working peers vs future council

  • Working peers (now): Claude (driver, here), Codex, AGY (Gemini), OpenCode (MiniMax 2.7). These are the live coding workers and reviewers.
  • Future council (later spec): local models on BC-250 inference workers + the L40S "brain". Not online yet; out of v0 scope. The peer abstraction must not assume a model is remote/cloud, so local backends drop in later without rework.

Step 0 — OpenCode/MiniMax integration spike (do FIRST, before v0)

Codex (codex) and AGY (agy) already have working CLIs and Claude-side skills. OpenCode/MiniMax 2.7 is the one unproven peer — opencode is installed (~/.opencode/bin/opencode) but its config is minimal, so the MiniMax 2.7 provider/model wiring is unvalidated. We de-risk it before committing the council architecture to it (empirical validation before scaling).

Spike acceptance criteria:

  1. opencode runs MiniMax 2.7 — provider/model configured in ~/.opencode/opencode.jsonc (or project config), confirmed with a trivial prompt round-trip.
  2. Non-interactive / headless invocation proven — driven from a Node/shell call (the way codex/agy are), returning output we can capture. This is the contract the future opencode-pty.ts adapter will implement.
  3. Review mode: given a diff + a review prompt, it returns a usable verdict.
  4. Worker mode: given a task in a scratch worktree, it makes a coherent edit.

Output of Step 0: a short findings note + the invocation contract, feeding the opencode-pty.ts adapter design. If headless OpenCode proves unworkable, that changes the v0 design — hence it goes first.

Architecture

Base (inherited from cortextOS, unmodified where possible)

  • src/pty/ — agent-pty.ts (base), codex-pty.ts, hermes-pty.ts. The multi-backend abstraction we extend.
  • src/bus/, bus/*.sh — Telegram, heartbeats, approvals, experiments, KB, tasks, cron. Reused as-is.
  • src/cli/, src/daemon/, src/hooks/, src/telegram/ — runtime.
  • dashboard/ — Next.js 14 dashboard.
  • templates/, skills/, community/ — agent templates and skills.
  • Stack: TypeScript strict, Node ≥20, tsup build, vitest tests, minimal deps.

Overlays (ours — additive, back-portable)

  • New PTY adapters as siblings to the existing ones:
    • src/pty/agy-pty.ts — Antigravity / Gemini CLI backend.
    • src/pty/opencode-pty.ts — OpenCode harness fronting MiniMax 2.7. Both implement the same agent-pty interface; genuinely upstream-valuable, so they ship as clean candidate PRs.
  • src/council/ — peer orchestration:
    • A worker dispatcher: given a workstream + a chosen peer, spawn it in an isolated worktree (parallel coding workers, Law 1).
    • A review fan-out: given a diff, run Codex + AGY + OpenCode in parallel, collect verdicts, aggregate to a pass/concerns summary (Law 2).
  • Hoff-geared skills/prompts under skills/ — additive, rebuilt for the Hoff's voice and workflow.
  • Theming/branding abstraction (Law 3 corollary) — uplift cortextOS so the dashboard and any rendered output read a theme (tokens + CSS) rather than hardcoded styles. Upstream-clean. The Hoff's theme ships as a separate bundle.
  • Scribe worker + theming uplift form the publishing & branding sub-project (own spec, see below) — kept out of the v0 critical path.

Enforcement surface

  • CLAUDE.md (repo root) — the four laws, so every agent session inherits them. Co-exists with the inherited cortextOS contributor doc (renamed if it collides).
  • CONVENTIONS.md — fuller convention: overlay/back-port rules, worktree workflow, peer roster, review protocol.
  • Advisory git hook (pre-push or pre-merge) — runs the tri-model review, prints verdicts, allows override via a documented flag (e.g. MYCORTEX_SKIP_REVIEW=1). Fits rapid iteration; enforced, not handcuffed.
  • BACKPORT.md — ledger of upstream-clean vs mine-only commits.

Data / control flow

Parallel coding workers (Law 1)

task ──▶ decompose into N independent workstreams
            │
            ├─ worktree A ─▶ peer (Claude|Codex|AGY|OpenCode)
            ├─ worktree B ─▶ peer
            └─ worktree C ─▶ peer
            │
            ▼
       integrate / review

Each workstream is an isolated git worktree so peers never collide on files.

Tri-model review gate (Law 2)

diff ──▶ council review fan-out (parallel)
            ├─ Codex   ─▶ verdict
            ├─ AGY     ─▶ verdict
            └─ OpenCode─▶ verdict
            ▼
      aggregate ─▶ pass / concerns  ──▶ git hook surfaces, override possible

Repo mechanic — adopt the fork, merge everything (decided)

myCortex becomes the go-forward home of the Hoff's thehoff/cortextos fork, with all his work consolidated in. The Hoff's stated approach (the divergence is "not that far ahead", so reconciliation is manageable):

  1. Land the fork into Gitea. Push from framework (~/GitHub/cortextos, already on GitHub origin) into the Hoff's git → Gitea lab as the myCortex primary. (The bootstrap myCortex repo's lab/origin identity is kept; cortextOS history + content come in.)
  2. Pull upstream main (grandamenium/cortextos) and merge — resolve the ~28-commit gap. Keep upstream remote for ongoing bidirectional flow.
  3. Merge in the feat/* branches one at a time, fixing as we go: connectors, branding/white-label, openai-runtime + openai-compatible-pty, then reconcile MCP against the (other contributor's) upstream MCP PR — prefer upstream, don't duplicate.
  4. Rebrand package.json → mycortex; preserve cortextOS LICENSE + attribution (MIT). Add the repo-root CLAUDE.md (five laws) + CONVENTIONS.md
    • BACKPORT.md.
  5. Remotes end state: lab (Gitea, primary/mine) · origin (GitHub, mine) · upstream (grandamenium, pull-only).

HARD GUARDRAIL — never push to upstream. upstream (grandamenium/cortextos) is fetch/pull only. We pull improvements down; we never push to it. "Back- portable" means PR-ready in principle — actually opening an upstream PR is a manual, Hoff-initiated action, never automated and never done by an agent. Local-first ownership (Law 4): the work stays mine.

Each merged feat/* branch is tagged in BACKPORT.md as (a) modular or (b) upstream-PR-candidate, per Law 3 — the tag records eligibility, not intent to push.

Error handling / edge cases

  • Peer unavailable (CLI missing / not authed): the dispatcher and review fan-out degrade gracefully — skip the missing voice, record it, never hang. Review with <3 voices is flagged in the summary, not silently passed.
  • Worktree collision / leftover: worktrees are named per workstream and cleaned on completion; stale worktrees are detectable and prunable.
  • Hook override: every skipped review is logged so the BACKPORT/audit trail shows where the gate was bypassed.

Testing

  • Follow cortextOS's vitest pattern; add unit tests for new code in tests/.
  • New PTY adapters: unit-test the adapter contract against the agent-pty interface (mock the child process).
  • Council dispatcher / review fan-out: unit-test aggregation logic and the graceful-degradation paths with mocked peers.
  • npm run build (tsc clean) + npm test green before any merge — same bar as upstream.

Publishing & branding sub-project (own spec — after v0)

A coherent, mostly-deterministic layer. Decomposed out of v0 so it gets its own spec → plan → build cycle, but captured here so the seams are reserved.

Theming uplift to cortextOS (Law 3 corollary)

Contribute a generic theming layer upstream: the dashboard (and rendered HTML output) load a theme — a set of CSS custom properties + fonts + two palettes — instead of hardcoded styles. Themes are vendored, no CDN (matches hoff-ui's own rule). Default theme stays cortextOS's; the Hoff's theme is an add-on bundle. This is the back-portable contribution; our brand is the overlay on top.

The Scribe worker (deterministic md→HTML publisher)

A plain Node.js worker (Law 5 — no AI) that looks like an agent on the bus.

  • Input: bus jobs (e.g. publish/render) and/or a watched markdown source tree (chokidar — already a cortextOS dep).
  • Job: convert markdown → branded HTML in the Hoff's house style, aligned to hoff-ui / hoff-docs / askew-docs branding. Mermaid pre-rendered, tables, code highlight, no em-dashes, Australian English (matches the narrative-docs house style the Hoff already uses).
  • Two served roots:
    • /documentation/ — readable HTML of reports, notes, specs, data. Uses the narrative theme (consumption).
    • /dashboard/ — operational views / status. Uses the dashboard theme (operation). Reconcile with the inherited Next.js dashboard during this sub-project's spec: the Scribe may render a lightweight static dashboard, or feed the Next.js one — decided then, not now.
  • Serving: a small static HTTP server (minimal deps, in keeping with cortextOS).
  • Rendering uses the theming abstraction above — so the worker is brand- agnostic and the Hoff brand is just the active theme.
  • Law 5 pilot. Baseline is a pure deterministic renderer (tier 1). The Scribe is also the natural pilot for a tiny local edge model (tier 2, ≤~1GB, mlx/CPU/GPU) on the fuzzier "HTML management" judgement — layout choices, summarising a report, picking the right theme/section treatment. Build deterministic first, measure, then trial the tiny model only where the deterministic path is genuinely awkward. Frontier peers are never in this loop.

Maps onto hoff-ui directly: narrative palette (pink/purple/green) for docs, dashboard palette (mint/cyan/amber) for ops; Geist + JetBrains Mono + Caveat; 1200px / 760px wraps; tokens from hoff-ui/tokens/.

Out of scope (later specs)

  • Local council backends (BC-250 / L40S models).
  • RAG / per-repo retrieval integration (myRAG, toolrag).
  • Dashboard rebrand and council telemetry views.
  • Workflow visualiser (see below).
  • Synthetic-data / LoRA training loop.

Workflow visualiser (captured requirement, later spec)

The Hoff wants to see agents move through workflow stages — for both the council and ordinary task pipelines. Reference: the "AIOS Pipeline" board — a horizontal staged DAG (e.g. Capture → Classify → Rules → Action → Process → Deliver), each stage a column of node cards carrying live status badges, with edges flowing left-to-right between stages, rendered in the hoff-ui theme (dark, pink/purple). Built on the inherited Next.js 14 dashboard.

Design seam to keep open now so this lands cleanly later: the council dispatcher and review fan-out must emit structured stage/transition events (node id, stage, status, timestamps) — not just return final results — so the visualiser can subscribe to a live event stream rather than being bolted on. v0 does not build the UI, but its events are shaped with this consumer in mind.

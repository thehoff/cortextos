myCortex — Branding Foundation Decision (council-reviewed)

Date: 2026-06-01 Status: Decided (architecture); implementation pending Method: 3-model design panel — Codex (gpt-5.4-mini), AGY (Gemini), OpenCode (MiniMax M2.7) — run in parallel, then synthesised. Raw panel outputs were in /tmp/panel-{codex,agy,opencode}.md.

The ask (the Hoff)

Establish branding FIRST (before the Scribe HTML tool and the rest of the fork consolidation). Use the Hoff's colours/brand, BUT aligned to the cortextOS base theming framework so the framework can be released with the base — the brand is one theme on top, not a hardcoded reskin. Any change to cortextOS base for theme/branding is a clean feature branch + PR, documented obviously (Law 3b). The hoff brand itself is a modular overlay (Law 3a).

Verified reality (the blocker the panel caught)

The base cortextOS dashboard already has a theming system, and it is NOT hoff-ui's:

  • next-themes with <ThemeProvider attribute="class" defaultTheme="light">.
  • shadcn + Tailwind v4; @custom-variant dark (&:is(.dark *)) — class-based dark mode (.dark), light default.
  • Font Sora (not Geist); shadcn CSS vars (--background, --foreground…).

hoff-ui uses :root[data-theme="narrative|dashboard"], Geist/JetBrains/Caveat, dark-first, pink/purple (narrative) + mint/cyan (dashboard).

These two systems fight (class+next-themes vs data-theme; light vs dark; Sora vs Geist; shadcn tokens vs hoff tokens). Reconciling them is the core technical problem — not a cosmetic reskin.

Council convergence (high confidence — all three agreed)

  1. Single source of truth = a brand schema, not raw CSS. A BrandPack / branding.json manifest describes semantic slots only: theme id, base theme (narrative/dashboard), token overrides, chart palette, typography, assets, PWA metadata. A small Node generator emits deterministic artifacts: brand.css (CSS custom properties), brand.mjs (theme data), a manifest, and a chart-palette JSON.
  2. Consumers ingest the generated artifacts via a thin adapter — never raw tokens. Dashboard, Scribe, and the future visualiser each import the brand package independently. No shared cross-surface TypeScript types. This keeps cortextOS mergeable and Scribe/visualiser decoupled (Law 3a).
  3. hoff brand = a pluggable package (e.g. packages/hoff-ui/ / @mycortex/brand-hoff). Base ships a neutral default pack + a single injection seam (resolveBrandPack() / the --white-label flag): load pack from file/path/env, apply pre-hydration CSS vars, then hydrate. No base component imports brand-specific values. If upstream rejects the hoff brand, the framework still ships; the fork points branding.json at the hoff pack.
  4. Consolidation order: branding-contract-and-pre-hydration + white-label- config first (co-dependent pair) → per-org-theme-overrides → design-token-export + brand-assets-code (either order) → cli-visual-polish last (isolated, lowest risk).

Repo reality (git-verified)

  • feat/branding-contract-and-pre-hydration is the common ancestor; white-label- config, per-org-theme-overrides, design-token-export, brand-assets-code are siblings off it (no single tip contains all) → sequenced multi-merge with likely sibling conflicts.
  • Every branding branch diffs ~10k lines from the stale fork/main because they also carry the connector stack — branding and connectors land together.

Risks (merged from the panel)

  • Blocker — theming-system clash: next-themes(.dark class) vs data-theme; the --white-label/brand layer must switch the full CSS-var set, not a subset, or both themes break.
  • Blocker — pre-hydration/FOUC: server and client must resolve the same pack, or Next.js flashes/!mismatches.
  • Blocker — Scribe has no renderer yet: tools/scribe/cli.mjs is declared in package.json but not written; the brand system needs a consumer to prove it.
  • High — token drift: CLI (src/branding) vs dashboard (dashboard/src/lib/ branding.ts) must stay in sync; add a test that enforces it.
  • Med — CLI/ANSI: terminal output can't use CSS; needs native colour codes.

Decision

Build the theming framework as a documented, upstream-clean feature branch + PR on the base (Law 3b), and the hoff brand as a modular pack (Law 3a), sharing the BrandPack contract. Reconcile the dashboard's next-themes/shadcn system by mapping hoff signal tokens onto the shadcn CSS-var contract and adding a data-brand/pack layer on top of next-themes' light/dark — not replacing it.

First action (council consensus)

Lock the BrandPack schema, build a minimal packages/hoff-ui token package (signal palette only: narrative pink/purple/green, dashboard mint/cyan/amber) as CSS custom properties + the Node generator, and a collision test proving the hoff tokens override the base cleanly — driving the dashboard AND Scribe end-to-end.

Process (the Hoff's directive)

  • Base-touching theming-framework work → branch feat/theming-framework (or consolidate the existing branding branches), PR-style, documented obviously (README/ADR + tests). Upstream-clean.
  • hoff brand → packages/hoff-ui modular pack, never edits base components.
  • Never auto-push to upstream; PRs are the Hoff's to open.
